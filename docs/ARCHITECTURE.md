## 1. 分层总览

```
┌─────────────────────────────────────────────┐
│ index.html / src/main.ts / src/style.css     │  入口与外壳（Round 01）
├─────────────────────────────────────────────┤
│ src/game/     游戏胶水层                      │  Phaser 场景、UI 装配；
│               （认识 Phaser，不认识设定）       │  把引擎服务接到画面上
├─────────────────────────────────────────────┤
│ src/engine/   引擎运行时                      │  循环、状态、加载、校验、事件、
│               （不认识 Phaser 之外的具体内容）  │  存档、系统（时间/战斗/图谱）
├─────────────────────────────────────────────┤
│ data/schema/  JSON Schema（数据契约）          │
│ data/base/    基础世界数据（按资源族分组，全 JSON）│  ← 内容唯一来源
│ mods/         mod 覆盖层（同名文件优先）        │
└─────────────────────────────────────────────┘
```

**引擎/数据分离的铁律**：

- `src/engine/` 与 `src/game/` 中**不得出现具体设定文本**（角色名、地名、台词、剧情数值等）；引擎只认协议（schema 定义的形状）。
- 一切世界内容经 `data/` 进入；改世界 = 改 JSON，不动代码。
- 校验内容：`data/schema/` 中的 JSON Schema 是引擎与资料作者之间的契约。

## 2. 启动流程与缺失数据的降级策略

Round 01 的切片式地图加载已由后续统一加载器取代。当前 Vite 将 `data/` 与 `mods/` 作为受限静态资料目录，生产构建复制资料并以相对基址 `./` 加载 `base/manifest.json`、`schema/`、`base/<resource.path>` 与已启用 MOD 覆盖；相对 URL 支持域名根路径和仓库子路径。缺失/HTTP 错误、JSON 无法解析、Schema 或语义检查失败时，场景显示结构化可读诊断。实际版本包只包含允许列表中的构建资源和说明，不带开发代码或依赖。Round 47 烟测当时从解包版本包子路径加载 26 项基础资源；Round 62 烟测按当时 manifest 核验 28 项，Round 67 时为 30 项，Round 74 扩展至 34 项资源，当前共 26 份 Schema。详细证据见 `DEVLOG.md`。

Round 02 已接入正式资料管线。`data/base/manifest.json` 列出资源 id、相对路径、schema id 和按顺序启用的 MOD。加载顺序为：Ajv 校验 manifest → 加载并编译被引用的 schema → 加载并校验基础资源 → 按启用顺序读取同路径 MOD 覆盖并重复校验 → 通过事件总线广播结果 → 场景消费资源。Round 03 起 manifest 注册地图/NPC/对话，Round 04 登记角色/门派/武学，Round 05 登记战斗遭遇，Round 06 登记物品/商店，Round 07 登记任务；Round 10 根据 `grid-map` schema 家族收集全部地图，并要求 `world-map` 资源解析出有效起始地图；Round 11 将知识节点与关系作为两个可选、独立 schema 资源登记，缺失任一者时以空集合继续，坏引用只隔离相关关系或对话选项；Round 14 登记**必需**的 `game-calendar` 历法资源，未登记或语义无效时提供可读错误并拒绝加载；Round 15 登记**必需**的 `climate` 资源，必须与历法月份完整分区且权重引用有效；Round 16 的 NPC 日程是 NPC 资源的可选扩展，逐项引用历法时段并按地图校验占位；Round 21 的 `faction-war-set` 为可选资源，跨资源检查入口格、两派、双方对手武学及结局知识节点；Round 74 起 `npc-set` 与 `quest-set` 也按 manifest Schema 汇总任意数量的资源，资源内的错误仍单独隔离并报告。地图、区域、图谱、历法、气候、日程和门派战协议均由 Phaser 无关模块执行。运行状态仍独立保存到浏览器本地存储，不混入世界资料。

Round 22 在上述流程中可选登记武学创制组件资源；它按 JSON Schema 与 Phaser-free 语义规则校验，缺失或错误只禁用 C 键创制入口，玩家自创定义则写入独立的运行时存档字段，不回写世界资料。该组件资源和对应 Schema 也支持同名 MOD 覆盖。

缺数据/坏数据的行为按严重度分级：

| 情况 | 行为 | 用户所见 |
|---|---|---|
| manifest、manifest/grid-map schema 或当前关键地图缺失/不可解析 | 资源不进入运行状态；场景显示诊断面板并停止装配 | 来源路径、HTTP/解析/schema 原因及修复提示 |
| 历法资源（game-calendar）未登记、缺失、schema 不符或语义无效（重复月份/时段 id、时段起点重复、缺零点时段、起始月/日/时刻越界、耗时越界） | 同上：历法是必需资料，整资源拒绝，不回退到硬编码历法 | 面板点名 `calendar.base` 与具体未通过的语义条目 |
| 气候资源（climate）未登记、缺失、schema 不符或语义无效（重复季节/天气 id、月份重叠/缺失/未知、天气权重悬空或总和为零） | 同上：气候是必需资料，整资源拒绝，不回退到硬编码天气 | 面板点名 `climate.base` 与具体未通过的语义条目 |
| 可选资源（NPC/对话/角色模板/门派/武学/战斗遭遇/擂台/门派战/物品/商店/任务/伙伴/知识图谱/结局/成就）或其 schema 缺失、不可解析、schema 不符、未通过语义校验 | 降级为警告；场景继续装配其余内容 | 地图与移动不受影响；HUD 显示"已禁用相应内容"警告行，控制台保留结构化诊断 |
| 成就集资源整体结构无效（id 不符、条目数越界）或集合级解析失败 | 成就系统关闭（装配结果为 null）并给出 warning；其余世界内容照常 | G 键提示"当前世界没有可用的成就资料。"；存档成就状态仍正常读写 |
| 单条成就坏（id 重复/无效、字段或条件越界、悬空人物/门派/知识引用） | 只禁用该成就，其余成就照常参与评估 | 同上；警告点名被禁用的成就与原因 |
| 单条 NPC 记录坏（引用不存在、坐标越界/阻挡、压出生点、同格冲突、id 重复） | 只禁用该 NPC，其余照常放置 | 同上；警告消息点名被禁用的 NPC 与原因 |
| 单个 NPC 日程时段不存在、坐标不可走/压出生点、与固定遭遇或其他时段 NPC 冲突 | 仅该日程项回退 NPC 基础位置并警告；基础 NPC 记录仍可用 | 同上；诊断包含 NPC、时段和冲突坐标 |
| 单段对话坏（起始节点/选项引用断裂、节点 id 重复）或对话 id 重复 | 只禁用该对话及引用它的 NPC，其余照常 | 同上 |
| 对话条件通过静态 Schema 但语义无效（例如同时提供的 `minValue` 大于 `maxValue`） | 只禁用该对话及引用它的 NPC；其他合法对话保留 | 同上；warning 点名段落与原因。静态 Schema 违规仍按资源级拒绝 |
| 单个对话选项的条件/效果引用坏（questId/itemId/npcId 悬空） | 只剔除该选项；其所在节点可能因此成为结束节点，对话与其余选项照常 | 同上；警告点名对话、节点与被剔除的选项 |
| 对话选项的 `timeOfDay` 条件引用历法未声明的时段 id | 只剔除该选项；同时段/其他选项照常 | 同上；警告点名 `引用无效时段` 与悬空 id |
| 对话选项的伙伴 id 引用坏 | 只剔除引用悬空伙伴的选项；伙伴集合与其他对话照常 | 同上；warning 点名无效伙伴 id |
| 单个对话选项的知识节点引用坏 | 只剔除引用悬空节点的条件/效果选项；其他对话照常 | 同上；知识图谱缺失时百科显示空态 |
| 知识节点/关系集合缺失，或图谱行重复/关系端点悬空 | 可选集合按空集处理；重复节点/关系保留首条，坏边逐条忽略 | 地图可继续探索；告警包含资源或条目位置与原因 |
| 角色模板/门派条目 id 重复 | 保留先声明者并警告 | 同上；警告点名重复 id |
| 单条武学坏（引用的门派不存在或已被禁用） | 只禁用该武学，其余照常索引 | 同上；警告点名被禁用的武学与悬空门派 id |
| 单条遭遇坏（地图/模板/敌人武学引用断、触发格越界/阻挡/压出生点/NPC/其他遭遇格、id 重复） | 只禁用该遭遇，其余照常放置 | 同上；警告点名被禁用的遭遇与原因 |
| 角色模板 `startingMartialArtIds` 含悬空引用/不满足起始条件/重复声明 | 只剔除该起始武学，模板保留可用 | 同上；控制台警告点名模板与武学 |
| 起始物品引用悬空、商店引用悬空或货架物品无效 | 起始物品只剔除该声明；坏货架条目只剔除该条；无有效 NPC 的商店禁用并警告 | 背包/其余有效商店与地图仍可用；坏 `shopId` 回退到 NPC 对话 |
| 单条任务有坏发布 NPC、目标物品/遭遇/谈话人物、前置引用或前置循环 | 只禁用该任务及依赖它的任务；重复任务 id 保留首声明者 | 其他任务、NPC、背包、战斗与地图仍可运行；警告列出任务 id 和原因 |
| 互斥分支组（同 `exclusiveGroupId`）有效成员不足 2 项或成员前置不一致 | **整组禁用**（含本来有效的成员），不留下假单选分支 | 其余任务照常；警告点名组 id 与每个被禁成员 |
| 战斗遭遇、物品、商店、任务或角色模板资源完全未登记或有效集合为空 | 无相应领域数据进入运行状态；玩家状态由首个有效角色模板独立创建 | 地图正常显示；没有有效物品时背包为空，没有有效商店/任务时 NPC 仍可交谈或显示空名录；控制台汇总已加载数量（可为 0） |
| NPC/对话资源完全未登记或有效集合为空 | 无可选内容进入运行状态 | 地图正常显示，底部状态行显示"暂无可交互人物" |
| 角色模板/门派/武学资源完全未登记或有效集合为空 | 无成长数据进入运行状态（后续系统按空集处理） | 地图正常显示；控制台汇总已加载数量（可为 0） |
| MOD 没有某资源的同路径文件 | 保留当前有效版本，无诊断 | 玩家不受影响 |
| MOD 覆盖不可解析、schema 不符或未通过注册的语义校验 | 跳过该覆盖，保留上一有效版本并记录 warning | 当前地图继续运行；HUD 显示 MOD 警告，控制台保留详细诊断 |

原则：**宁可小而完整地跑起来，并把问题说清楚；绝不让玩家面对白屏或裸异常。**

## 3. JSON Schema 校验（Ajv，Round 02 已接入）

- 当前 `data/schema/` 有 26 份 draft-07 JSON Schema：`manifest`、`grid-map`、`world-map`、`game-calendar`、`climate`、`knowledge-nodes`、`knowledge-edges`、`npc-set`、`dialogue-set`、`character-profiles`、`faction-set`、`martial-arts-set`、`battle-encounters`、`items-set`、`shops-set`、`quest-set`、`companion-set`、`arena-set`、`faction-war-set`、`martial-art-components`、`meridian-set`、`equipment-forge-set`、`alchemy-set`、`ending-set`、`achievement-set` 与 `content-package`。当前基础 manifest 登记 34 项资源、覆盖 24 个资源 Schema 家族；`manifest` 与 `content-package` 是独立契约，不计入这 24 个世界资源家族。
- Ajv 8.x 在加载期校验 manifest、基础资源和每份 MOD 覆盖（开发/生产相同），不在游戏循环内反复校验。
- 跨字段规则分层完成：地图尺寸/出生点、世界图地图/区域/关口/事件引用、关口坐标和可走性、历法 id/时段起点唯一性与零点时段存在性、气候季节对历法月份的完整分区及天气权重引用等由语义解析补足；世界图跨地图装配后还会排除与 NPC/战斗遭遇重叠的关口或区域事件。角色成长、武学、物品/商店、任务与对话引用仍按原有模块逐项校验；对话范围顺序由防御解析器隔离。失败时只禁用受影响的最小条目，世界图起始地图、历法与气候等关键资料无效则提供可读启动错误。
- 错误输出为结构化诊断（来源、资源、消息和字段路径），可被事件总线订阅并显示在场景。

## 4. mod 覆盖：同名文件优先级（Round 02 已提供基础能力，Round 35 增强作者工具）

规则（数据面细节见 `docs/DATA-GUIDE.md` §5）：

1. **路径即身份**：`mods/<modId>/<与 data/base/ 相同的相对路径>` 覆盖基础数据中同名文件，整文件替换、不做字段级合并（合并语义复杂，明确不做）。
2. **优先级**：`mods/` > `data/base/`；多个 mod 同时启用时，按 mod 加载清单的**声明顺序**应用，后者覆盖前者。
3. 覆盖后的数据仍必须通过同一 schema 校验——mod 不能绕过契约。
4. 覆盖关系在启动时可追溯（哪个文件被哪个 mod 覆盖），成功来源与错误均经事件总线输出。
5. 根目录 `mods/` 的 JSON 由 Vite 开发中间件安全提供，并由生产构建插件复制；只提供仓库 MOD 根目录内的 JSON，拒绝目录穿越与非 JSON 路径。

启用顺序维护在 manifest 的 `enabledMods` 数组中，后声明 MOD 优先。当前 `mods/example/` 是未启用的演示覆盖。

## 5. 开发模式资料热重载（Round 36）

- `scripts/data-hmr-plugin.mjs` 注册 Vite Environment API `hotUpdate` 插件，只把仓库内 `data/**/*.json` 与 `mods/**/*.json` 的新增、修改、删除广播为 `wuxia:data-change` 自定义 HMR 事件，并返回空模块列表，阻止这些内容文件触发模块传播/整页刷新。源码、非 JSON 与仓库外路径不转发。
- `src/game/data-hot-reload.ts` 只在 Vite 开发模式订阅事件；80 ms 内同一文件的连续通知合并为末次状态。场景关闭时退订并取消未发送批次。菜单按原页面重读共享 `loadWorldData`，刷新角色模板或展示资料错误。
- 游戏场景把通知暂存到安全边界：不在移动、战斗或面板开启中替换数据；重载请求期间关闭场景输入。运行状态用 `captureSaveSnapshot` 保存在内存中（不写用户存档槽），经新世界的 `planSnapshotRestore` 兼容预检后再由 `restoreRunState` 重建。基础 JSON/schema 使世界加载失败或快照不兼容时保留旧世界与运行字段并显示可读提示。由于地图、NPC、任务、图谱等资料存在跨资源引用，当前按 manifest 完整重读和组装世界，而非局部原位替换。
- 加载期间再次修改 JSON 会排队触发后续重读；初始世界加载期间的变更也会在首次装配后补跑。HMR 插件 `apply: 'serve'`，客户端桥接经生产打包校验不会进入发布 JS。作者工作流与局限见 `docs/DATA-GUIDE.md` §6。

## 6. 静态版本包与授权边界（Round 47）

- `vite.config.ts` 以相对 `./` 作为生产资源基址；加载器将该基址与 `base/`、`schema/`、`mods/` 路径拼合，支持挂载在根路径或仓库子路径。
- `npm run package:release` 从生产 `dist/` 和明确的发布说明文件构造临时 staging；包内 manifest 记录其余每份文件的长度与 SHA-256，归档有单独 checksum。打包白名单包含玩家/MOD 手册，解包 smoke 会验证其存在。
- 静态版本包只能使用构建时携带的 MOD。新增覆盖要由维护者编辑资料、启用并校验，再重新构建和部署；开发 HMR/命令行内容包导入不会变成浏览器版的动态安装功能。
- 版本包带运行时 npm 依赖的 package license 元数据与随包许可证文本，不授予项目代码、原创数据或参考网页的授权。项目无独立 `LICENSE`；人工 Pages workflow 是可用配置，不表示已经部署。
- Round 72 的 Vite 8/Rolldown `output.codeSplitting.groups` 将 `phaser` 依赖输出为 `phaser-runtime-<hash>.js`，应用逻辑保留在独立入口。它让两者可以分开缓存，但入口对 Phaser 是静态 import，故游戏启动时仍会加载两个 chunk；不将此项描述为懒加载或首屏总流量下降。`scripts/audit-round-72-chunks.mjs` 在打包前校验 chunk 边界和本地 JS 引用，Round 47 子路径 smoke 再逐个请求已归档的 chunk/import。

## 7. 代码组织约定

- `src/engine/` 内模块不 import `src/game/`（单向依赖：game → engine）。
- 引擎对外暴露 TypeScript 接口（协议优先），数据形状由 schema 与接口共同约束。
- 每个 Round 的实现变更记录于 `DEVLOG.md`，架构级变更必须先补 ADR。
- Round 02 的 `EventBus` 是同步、泛型类型约束、与 Phaser 无关的引擎模块；订阅返回精确退订函数，`once` 在回调前移除自身。
- Round 03 的 `npc-placement.ts` / `dialogue-graph.ts` 是与 Phaser 无关的引擎模块（解析、校验、索引、会话状态与邻接选择）；Phaser 呈现只出现在 `src/game/dialogue-ui.ts` 与场景装配中。NPC 占用格阻挡、E 键四方向邻接交互（最近优先、等距按 NPC id 决胜）与对话期间的移动输入隔离均在场景层接线。

### Round 13：师门规则与对话事务

`faction-system.ts` 是 Phaser-free 的门派规则模块：接收已解析的门派、角色、社会状态、任务状态和当前对话 NPC，统一检查入门条件并操作唯一师承关系。`dialogue-runtime.ts` 通过 staged copy 原子应用拜师、退门惩罚、门派武学遗忘和授艺；`save-system.ts` 将师门身份作为可空 v1 字段保存，恢复时把失效门派/师父隔离为无门派并报告 warning。导师、门槛、退门后果和对白均来自数据文件。

### Round 14：数据驱动历法与游戏时钟

`game-calendar.ts` 是 Phaser-free 的历法协议与时钟引擎：防御解析并语义校验月份/时段/起始时刻/动作耗时（Ajv 语义校验器在资源层拒绝无效历法），`GameClock` 以单一"已过分钟数"为权威状态，按需折算年/月/日/分钟并做循环时段查询——零点时段由校验保证存在，跨午夜时段因此无需特判。`grid-scene.ts` 只在动作确实完成后调用推进：成功移动一步、成功通过关口旅行和 V 键等候分别消耗资料配置的分钟数，被阻挡的移动、被拒的传送与任何打开中的面板一律零消耗。时间 HUD 显示历日/时刻/时段；昼夜调色层以固定深度带（世界 0 < 调色 50 < HUD 60 < 面板 1000+）夹在世界图像与 UI 之间，按当前时段照度渐变，区域切换重建世界层后仍稳定覆盖。`dialogue-runtime.ts` 的 `timeOfDay` 条件读取时钟当前时段 id，装配期对照历法剔除悬空时段引用的选项。存档保存分钟计数而非派生日期，旧 v1 快照缺字段时从历法起始时刻恢复。

### Round 15：确定性季节天气

`climate-system.ts` 不依赖 Phaser，负责气候资料防御解析和确定性日天气：季节必须恰好划分已解析历法的全部月份，季节权重只能引用现有天气且总和为正；同一个 u32 世界种子和历日通过确定性 32 位混合得到固定权重 roll。新开局生成并固定世界种子，`save-system.ts` 将其保存为 v1 `worldSeed`，Round 14 及更早快照缺字段时归一到固定值 1。`grid-scene.ts` 按当日季节/天气更新 HUD、世界调色和雨雪程序粒子；动作成本只对成功网格行走增加天气 `stepMinutes`，不修改日历旅行与等候成本。季节/天气名、视觉参数、权重和步耗时全部来自 climate 资源。

### Round 16：NPC 历法日程

`npc-schedule.ts` 不依赖 Phaser：它将可选 `schedule` 项对照当前历法时段与 NPC 所属地图编译为逐时段位置表，并以稳定顺序检查地图通行、出生格、固定遭遇与同格冲突；单项无效时保留 NPC 并回退基础位置。场景只在时段变化、开局/读档和到达新区域时重算人物占位，玩家格优先；迁移后同时更新标记、姓名牌、碰撞索引和交互目标。存档不新增 NPC 坐标字段，`elapsedGameMinutes` 是唯一派生输入；恢复预检使用快照时段、地图、玩家格和当时有效遭遇解析真实 NPC 占位，避免以日间不适用的基础坐标误拒存档。完整协议见 `docs/NPC-SCHEDULES.md`。

### Round 17：条件奇遇与传闻发现

`world-map.ts` 扩展为纯 TypeScript 区域事件协议：防御解析 `conditions` 的知识节点/时段/天气条件组，组间 AND、组内 OR；`selectTriggeredRegionEvents` 根据位置、已知线索、当前历法时段和气候返回满足的事件，不修改任何运行状态。世界加载器把有效图谱节点、历法时段和天气 id 交给 `assembleWorldMap`，坏引用只隔离对应事件。GridScene 在移动完成、跨区到达和原地等候后检查当前格；等待摘要和命中的事件文案合并，一次性状态仅在成功触发后进入既有完成集，发现节点并入既有百科状态和 v1 存档。内容只读取事件文本与图谱标题，不在协议中写入具体人物/地点常量。

### Round 18：统一社会声望规则

`social-state.ts` 以 `SocialChange` 统一善恶、江湖个人声望、逐派声望和逐 NPC 关系的 signed delta 与范围钳制；`factionRenown` 以 faction id 为键，未出现的门派中立为 0。`dialogue-graph.ts` / `dialogue-runtime.ts` 新增 `factionRenown` 区间条件与 `adjustFactionRenown` 效果，跨资源装配检查 faction id，效果仍在 staged copy 中原子提交。门派 admission 可配置 `minimumFactionRenown`，departure 的 `factionRenownDelta` 只影响该派。`save-system.ts` 把门派声望写入 v1 `social.factionRenown` 列表，缺失字段视为空列表、移除门派逐项过滤；师门页并列显示全局善恶/声望与每派声望。

### Round 19：同行伙伴

`companion-system.ts` 仅依赖地图与伙伴资料，负责伙伴协议解析、有效 NPC 引用装配、单人队伍状态和安全跟随格选择。`dialogue-runtime.ts` 将招募/暂离纳入现有 staged-copy 事务，引用装配另校验 companion id；具体伙伴名、说明和攻/疗专长来自 `companions` 数据资源。GridScene 按当前队伍把伙伴 NPC 从静态日程/碰撞布局中过滤，以独立程序标记跟随玩家；该 NPC 的关系值仍在既有社会状态里，伙伴可跨区域跟随且不阻挡网格。`turn-based-combat.ts` 仅在成功玩家行动间隔满足时执行平伤或定值治疗支援，支援战报单独标记。P 键伙伴页呈现关系与专长，并能暂离。v1 存档添加可空 `activeCompanionId`；旧档缺字段按 null，恢复时过滤已删除伙伴。

### Round 20：擂台连战

arena-challenge.ts 防御解析擂台/对手/战绩协议，装配时校验入口地图格、角色模板、敌方武学、彩头物品及与出生点/NPC/野外遭遇/其他擂台的冲突。擂台入口独立标记；E 面板展示资料赛程、完整奖励与本地战绩，Enter 报名后依次构造普通 CombatSession。每轮仍由通用成长/伙伴规则处理胜利，但不调用野外遭遇任务信号；中途败退不发奖，夺魁按入口时预检过的背包/货币空间一次性领奖。arenaRecords 保存在 v1 快照；Round 19 及更早旧 v1 档读取时缺省为空。协议及玩法边界见 docs/ARENA_DESIGN.md。

### Round 21：门派战与世界后果

`faction-war.ts` 是 Phaser-free 的可选战事资料协议：装配验证地图入口、参战门派、两派各阶段的对手武学及胜/平/负的知识节点；坏入口或跨资源引用只隔离对应战事。入口使用独立标记和 E 报名面板，在籍参战门派弟子按对手阵营选用该派专属敌手数据，连续复用 `CombatSession`，不触发普通地图遭遇任务信号。阶段胜利积累贡献，败阵后恢复并续战；达到门槛为胜、部分贡献为平、零贡献为负，撤退则提前按现有贡献结算。结果数据分别调整个人声望、己方及对方门派声望，并发现可供百科和两派导师 `knowledgeKnown` 对话读取的会盟节点。v1 快照保存报名/结果计数与贡献记录，旧档缺字段为空；MOD 移除战事时只过滤对应记录。详见 `docs/FACTION_WAR_DESIGN.md`。

### Round 22：玩家自创武学

`martial-art-forge.ts` 只依赖组件协议与角色/背包状态，不依赖 Phaser。可选 `martial-art-forge-components` 资源提供招式、架势、吐纳三槽组件，JSON Schema 与语义解析共同拒绝重复 id、无效槽位/类型和值域；缺失或坏资料降级为创制入口不可用。纯规则合成器规范化玩家名称，按组件结算功力、内力与银两，限制自创数量、预算和作品 id；注册前完成全部拒绝检查，再一次性扣款、加入完整自创作品并授予玩家。GridScene 将玩家作品与基础武学合并到普通战斗、擂台和门派战会话；C 键面板只负责选择/预览/提交。v1 快照保存作品完整定义；旧档缺字段为空数组，恢复时重新执行命名空间、容量、名称、作品形状和功力上限校验，并允许玩家已学列表引用快照自带作品。详细规则见 `docs/MARTIAL_ART_FORGE.md`。

### Round 23：经脉效果作为独立派生来源

经脉资料由 `world-loader` 作为可选 `meridian-set` 资源验证与装配，并跨引用物品 id；悬空材料仅禁用该节点及其后继。Phaser-free `meridian-system` 负责节点依赖图、解锁交易、修为结算和加成汇总。`CharacterState` 只存运行修为、节点 id 和独立派生奖金对象；有效属性重算为基础属性 + 装备 + 经脉，生命/内力上限由角色公式与两种加成来源共同重算。战斗引擎只选配经脉资源规则，不引用具体人物/节点资料。

`save-system` 持久化修为和已打通节点 id；恢复预检对照当前有效节点集合做次要引用过滤。节点奖金不序列化，场景在装配当前资料后重算；没有有效经脉资源时既有经验、任务、战斗和装备流程保持可用。

### Round 24：装备锻造作为普通物品转换

`equipment-forge.ts` 是无 Phaser 的可选资料协议、跨引用装配和交易事务。世界加载器把 Schema 错误按可选内容处理；工位再按地图可走格、出生点、全部 NPC、遭遇、擂台、门派战和其他工位校验。有效站位进入日程占位集合；坏配方按工位/配方最小单元隔离。引擎只识别通用 `itemId`、物品类别、装备槽、属性奖金和银两，不认识具体世界名称。

交易先以只读条件判定材料、正银两成本和未装备基础装备，再在克隆背包中模拟扣料和结果容量，整体提交库存字段。结果是普通 `ItemRecordData`，穿戴调和、战斗和 save-system 无需扩展；收集任务在场景回调中接收新的物品数量快照。没有锻造资源时其他玩法保持可用。

### Round 25：炼丹复用物品与知识进度

`alchemy-system.ts` 以可选 `alchemy-set` 资料声明地图药炉、发现节点、杂项药材、费用及悟性结果阶梯。Schema 在加载期校验字段，解析/装配层再验证地图占位、资源引用、普通消耗品类别及恢复量单调性；坏单条工位/配方隔离并报告 warning。工位按图格占用 NPC 日程，与锻造、擂台、遭遇入口互斥；药炉交互由 Phaser 胶水层接到独立键盘面板。

配方解锁是既有 `knownKnowledgeNodeIds` 的投影，对话的 `discoverKnowledgeNode` 效果负责授方。引擎按当前有效悟性挑选最高已达结果，在只读资格验证后于库存副本扣药材、银两并模拟产出，所有检查成功才提交。成药沿用普通 consumable，任务收集计数、背包使用、百科发现、存档和 MOD 移除过滤都复用既有机制；没有炼丹资料时其余世界照常启动。

### Round 26：图谱驱动的社交记忆

`SocialState` 分别保存玩家社会值与 `npcKnowledge: Map<npcId, Set<nodeId>>`。加载世界时，NPC 起点的有效 `knows` 边生成静态记忆；对白 `shareKnowledgeNode` 只把玩家已知的有效节点写入当前对话对象，`npcKnows` 只读取该 NPC 私有集合。对话执行仍用 staged copy，新增记忆也深拷贝、统一提交，因此后续效果拒绝不会泄漏前面分享。

知识图谱人物边可以附带 `attitudeSpread`。关系对白效果先按既有关系范围结算直接目标，再把实际变化乘边系数传播给该方向的一跳人物；不递归，并沿用原有 clamp。有效人物端点以外的边只丢掉传播字段并给 warning，旧无系数边保持原行为。v1 `social.npcKnowledge` 是可选快照字段；读档逐 NPC/节点过滤后与当前静态知识合并，旧档缺字段仍可用。

### Round 27：数据驱动结局判定

ending-system.ts 是 Phaser-free 结局协议：它解析可选 ending-set，按任务状态、善恶/声望区间、人物关系、门派身份/声望和玩家见闻纯读评估全部条件，并在资源装配期校验每个结局的图谱节点/跨资源引用。结局集合、叙事文本、终章格和条件阈值来自 MOD 可覆盖的 JSON；终章格要避开静态世界对象，并加入 NPC 时段排位的阻挡集合。GridScene 只负责渲染入口标记、打开 EndingPanel、传入当下只读旅程状态并把已确认结局呈现为终章；不让场景持有剧情规则，也不改任务/社会值。

### Round 28：资料驱动成就（已验证）

`achievement-system.ts` 是 Phaser-free 的成就协议与规则模块：防御解析器在 Ajv 之外逐条隔离坏成就，`assembleAchievementSet` 在世界装配期对照当前人物/门派/知识节点集合丢弃悬空引用（只禁用对应成就）。评估是纯函数——输入当前旅程上下文，输出逐条件进度投影，不修改任何状态；`unlockReadyAchievements` 在此之上锁存新达成 id，保证一次性领奖幂等。`world-loader.ts` 把 `achievement.round-28-set` 作为可选资源接入既有解析/装配管线。

GridScene 负责玩法收口与奖励结算：战斗胜利、锻造与炼丹成功分别递增三个单调饱和计数器；状态行刷新、对白确认后与 G 键面板打开前重评成就，奖励经验经 `grantExperience`（联动经脉修为）与货币钳制安全入账，解锁提示与诊断日志只出现一次。`achievement-ui.ts` 的 G 键面板按 priority 排序展示锁定/进行中/已解锁状态、逐条件进度与奖励；成就列表和多条件详情可独立聚焦、滚动。`save-system.ts` 以 v1 可选 `achievementState` 保存历史解锁 id 与计数器，旧档缺字段归一为空，id 不按当前资料过滤（MOD 移除再启用不重复发奖）。协议细节与专项/回归验证结果见 `docs/ACHIEVEMENTS.md`。

### Round 78：地图行级遮挡与角色统一排序

游戏场景保留静态地面合成图，并把带 `depthSort: "y"` 的地图图层编入独立透明前景纹理。前景按非空地图行裁成 Phaser 图片，玩家、NPC、伙伴、名字牌和这些行切片共用一个世界场景容器；渲染深度由人物脚底 y 与前景行底边决定。同一行的前景使用微小稳定偏移盖住人物，避免深度相等时依赖添加顺序。切换地图时玩家会从旧容器摘下再加入新容器，避免区域重建销毁玩家对象。

NPC 的 `spriteFrames` 由数据提供，`npc-placement.ts` 负责结构解析和逐帧图集范围交叉校验；引擎只接收四向帧映射，不包含人物名/服饰规则。没有该字段的旧资源继续使用 `spriteFrame` 或地图默认帧。Map art cache key 分别覆盖完整地图缩略图、地面底图和 y-sort 前景，并将绘制通道/尺寸/帧 GID 纳入 key，避免数据热重载复用另一渲染通道的旧纹理。Canvas 合成关闭平滑插值，导出 PNG/Spritesheet 由 nearest-neighbor 纹理采样。`world-map.ts` 在固定区域事件上承载可选 `interaction`（prompt/range/approachDirections）；事件条件与 once/knowledge 结算共享原路径，场景只提供可通行视线判断、输入优先级与朝向表现。旧事件不声明 interaction 时仍踏入触发。
