# Round 00 计划

## 本轮目标

为一款原创武侠 RPG 建立可运行、可长期迭代的工程起点。完成有限且有来源标注的《白金英雄坛说》系列体验调研，确定技术栈和数据边界，建立核心设计文档与后续迭代路线；本轮不实现垂直切片玩法。

## 用户故事

- 作为玩家，我希望新作品保留小屏 RPG 的自由探索、NPC 交互、成长、武学和江湖选择体验，同时拥有独立世界观和原创内容。
- 作为开发者/资料作者，我希望引擎规则与可替换的世界资料分离，并能在今后校验数据、覆盖默认内容。
- 作为维护者，我希望从第一轮开始保留决策依据、验证命令和可逐轮追溯的路线图。

## 验收标准

1. 本轮先有计划，再写实现与文档；范围限定 Round 00。
2. `docs/REFERENCES.md` 记录研究来源、授权/使用边界；`docs/ORIGINAL-FIDELITY.md` 将有证据的原作系列体验与本项目映射分开说明，不搬用原作角色、地名、剧情或素材。
3. 建立 GDD 初稿与 `docs/ADR.md`；架构选择说明依据、约束及未决风险。
4. 建立建议目录的数据/引擎骨架，并创建可安装、可构建的 TypeScript + Phaser + Vite 项目；未来数据通过 schema 校验及 mod 覆盖的设计有文档记录。
5. `ROADMAP.md` 含 Round 00 到至少 Round 50 的逐轮计划；更新 `CHANGELOG.md`、`DEVLOG.md`。
6. 执行依赖安装和生产构建，记录实际命令与结果；所有变更纳入 `round-00: ...` Git 提交。

## 可验证子任务

1. **研究与设计基线**：核对历史/玩家来源与官方技术资料；编写来源清单、原作体验对照、GDD 和 ADR。验证：检查每条对照的证据范围和授权说明。
2. **工程起点与迭代治理**：初始化独立 Git/Vite 项目，建立引擎、游戏、数据、文档、迭代目录，写入 51 轮路线图与开发日志。验证：依赖安装成功、生产构建成功、目录清单与计划一致。

## 涉及文件

- `package.json`、锁文件、Vite/TypeScript 配置、`index.html`、`src/`
- `src/engine/`、`src/game/`
- `data/`（世界观、角色、地图、任务、对话、知识图谱、物品、武学、门派、结局）
- `docs/`（GDD、ADR、参考来源、原作对照、架构与资料规范）
- `iterations/round-00/plan.md`、`ROADMAP.md`、`CHANGELOG.md`、`DEVLOG.md`

## 风险

- 可检索的《白金英雄坛说》资料多为回忆文章、攻略或衍生作品说明，未发现可作为完整官方规格的公开资料；对照表须标明证据等级，不把整个系列或衍生作品细节误称为白金版定论。
- Phaser 3 是需求建议的默认项，但 Phaser 4 已进入正式版本线；Round 00 将依据官方版本和当前 Node 环境确定一个固定主版本，并写入 ADR，后续不可随意更换。
- 原作、衍生游戏和第三方素材的授权不清；本轮仅记录研究与摘要，不导入原作文本、名称、美术或音频。
- 当前工作区没有目标仓库；在单独的 `wuxia-rpg/` 子目录初始化仓库，避免改动其他项目。

## 预计人类工程师工时

约 2–4 小时（资料交叉核验 30–60 分钟，设计/架构文档 45–90 分钟，工程初始化 30–60 分钟，构建与提交检查 15–30 分钟）。

## Round 00 研究补记：白金版社区机制线索

### 目标与用户故事

补充核验一份明确谈到《白金英雄坛说》的早期社区问答/攻略转载，将可用于本作高层体验对照的输入与无法独立验证的具体细节分开。作为读者/设计者，我可以追溯“网格行走、NPC 动作菜单、回合制战斗”等对照信息的来源与置信度，而不会把社区攻略当作官方规格。

### 验收标准

1. 在参考清单登记来源 URL、页面性质、授权状态、用途及证据边界。
2. 在原作体验对照表新增仅涉及高层交互形式的条目，标为低置信度社区转述，并映射到本项目既有相关轮次。
3. 不复制页面文字、原作专有名称、剧情细节或素材；不据此改写本作世界内容。
4. 更新本轮开发/变更记录及路线图注记，检查文档差异并完成生产构建、Round 00 格式提交。

### 可验证子任务

1. 检查问答页作者说明和内容语境，判断其是否能作为独立于现有 go1980 文章的社区证据，并限定可安全摘要的粒度。
2. 登记来源并补充带低置信度标签的机制摘要与映射，确保不引用同页转帖中的角色/地点/结局细节。
3. 更新日志/路线图，复核来源编号、原创性边界、构建和 Git 状态后提交。

### 涉及文件

- `iterations/round-00/plan.md`
- `docs/REFERENCES.md`
- `docs/ORIGINAL-FIDELITY.md`
- `DEVLOG.md`、`CHANGELOG.md`、`ROADMAP.md`

### 风险与预计工时

- 风险：问答内容由用户提交且转载自另一社区，可能混合不同版本或不准确攻略；只记录低置信度、非专有的交互/战斗类别，不将细节扩展为白金版定论。
- 预计人类工程师工时：约 30–45 分钟，分为来源核验、证据限定、文档与提交检查三段。

## Round 00 参考清单编号与授权状态复核

### 目标与用户故事

审计 `REFERENCES.md` 的来源标识与授权/使用字段。作为读者和后续贡献者，我能从原作对照中的证据编号唯一定位到历史来源，区分技术文档与软件包许可，并看清哪些授权已核实、哪些只作事实查阅。

### 验收标准

1. 历史来源与官方技术资料在参考清单中使用唯一、连续且可追溯的编号；`ORIGINAL-FIDELITY.md` 的引用仍准确指向历史来源。
2. 每项来源均可见 URL、来源性质、授权状态/许可依据、项目用途及必要的证据边界；未核实许可不得写成已获授权。
3. 不复制第三方文章、文档、代码或媒体，不改动已冻结技术栈或后续轮次实现。
4. 检查编号与交叉引用，运行 `npm run typecheck` 和 `npm run build`，更新 R00 变更/开发记录及路线图后提交 `round-00:`。

### 可验证子任务

1. 核对历史来源编号、原作对照引用及官方技术来源编号，列出重复或悬空引用。
2. 明确技术文档的许可核验状态与事实查阅边界，区分官网文档和 npm 包许可证元数据。
3. 更新来源清单、日志/路线图，执行编号搜索、类型检查、生产构建与 Git 差异检查。

### 涉及文件

- `iterations/round-00/plan.md`
- `docs/REFERENCES.md`、`docs/ORIGINAL-FIDELITY.md`
- `CHANGELOG.md`、`DEVLOG.md`、`ROADMAP.md`

### 风险与预计工时

- 风险：网页授权声明不明确时不能推断为开放许可；重编号时不可改变历史来源在原作对照中的含义或证据等级。
- 预计人类工程师工时：约 30–45 分钟，分为编号审计、授权边界整理、交叉引用和构建验证三段。

## Round 00 GDD 现状标注复核

### 目标与用户故事

让 GDD 的文档状态与当前已完成轮次、实际存在的数据契约保持一致。作为后续设计和实现者，我能区分目前已落地并经数据加载器校验的内容族与尚待规划的数据族，不会按过时的 Round 02 文案误判项目状态。

### 验收标准

1. GDD 清楚标注为持续维护文档，并准确反映已更新至 Round 09。
2. GDD 的数据 Schema 概述与当前 `data/schema/`、基础 manifest 及加载器契约一致；不把尚未实现的系统写成已落地。
3. 更新 Round 00 变更/开发记录与路线图，运行 schema 资源映射检查和生产构建后提交 `round-00:`。

### 可验证子任务

1. 对照 GDD、manifest、schema 目录与架构说明，找出过时的轮次状态和数据族清单。
2. 修订 GDD 文档状态和当前 Schema 覆盖说明，保留未来系统为待实现的状态。
3. 更新 Round 00 日志，校验 manifest schema 引用、类型检查和生产构建，并复核提交差异。

### 涉及文件

- `iterations/round-00/plan.md`
- `docs/GDD.md`
- `CHANGELOG.md`、`DEVLOG.md`、`ROADMAP.md`

### 风险与预计工时

- 风险：Schema 文件存在不等于某份资源已在 manifest 启用；描述当前范围时需同时核对 manifest 与 Ajv 加载路径。
- 预计人类工程师工时：约 20–30 分钟，分为文档现状审计、状态说明修订、资源映射与构建验证三段。

## Round 00 GDD 核心系统设计补充

### 目标与用户故事

为 GDD 增加面向玩家体验的系统目标总览，补足核心循环之外的战斗、任务、物品、社会状态、模拟、存档与 MOD 设计边界。作为策划和后续实现者，我能看出各系统预期的玩家反馈、共用的数据驱动原则，以及哪些已经落地、哪些仍在路线图中。

### 验收标准

1. GDD 覆盖探索、NPC/对话、任务/事件、成长/门派/武学、战斗、物品/经济、社会后果/结局、时间天气模拟、存档/设置/MOD。
2. 每项均区分设计目标与当前实现/计划状态，状态与 `ROADMAP.md` 和已有实现一致；不把后续功能写成已实现。
3. 更新 Round 00 计划、GDD、变更/开发日志和路线图，核对表格状态、运行生产构建并提交 `round-00:`。

### 可验证子任务

1. 逐项比对 GDD 当前循环/里程碑、ROADMAP 和现有系统文档，确认目标系统及实际状态。
2. 编写系统目标矩阵，注明体验规则、数据/引擎责任及轮次状态，避免把原作事实与原创设计混写。
3. 更新文档索引与日志，检查 R00 对照边界、状态一致性、构建和 Git 差异。

### 涉及文件

- `iterations/round-00/plan.md`
- `docs/GDD.md`
- `CHANGELOG.md`、`DEVLOG.md`、`ROADMAP.md`

### 风险与预计工时

- 风险：把路线图目标误写成当前可玩功能，或把项目原创系统表述成原作事实；表格须显式区分当前状态与目标设计。
- 预计人类工程师工时：约 30–45 分钟，分为系统范围核对、矩阵编写、状态审阅和构建提交四段。
