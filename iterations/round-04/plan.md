# Round 04 计划

## 本轮目标

建立角色基础属性与经验成长、门派和武学的数据模型，为后续战斗、拜师、存档和 UI 提供稳定协议。本轮实现一套可校验的初始角色模板、原创门派/武学资料，以及与 Phaser 无关的进度计算和习得资格规则；暂不实现角色创建/拜师/修炼界面或战斗效果。

## 用户故事

- 作为玩家，我希望角色拥有清晰的基础属性，积累经验后能升级并按角色成长配置提升属性。
- 作为资料作者，我希望能以 JSON 定义角色模板、门派和武学，并用 Schema 与跨资源检查发现错误。
- 作为后续系统作者，我希望读取同一份通用数据模型，能计算升级门槛、派生生命/内力上限，并判断角色是否满足武学门槛。

## 验收标准

1. manifest 登记角色模板、门派、武学三种资源；各有 draft-07 Schema，Ajv 加载校验成功。
2. 数据提供 1 个可运行的初始角色模板、3 个原创门派与至少 6 种原创武学；属性、成长参数、门派名称/宗旨、武学名称/类别/门槛全部来自 JSON。
3. 通用引擎模型防御性解析三类集合，校验唯一 id 和武学门派引用；坏的可选资源不会阻止已有地图/NPC/对话切片启动，诊断可读。
4. 角色进度逻辑可从模板创建状态、按递增经验曲线计算升级、一次性处理跨级经验、应用逐级属性成长/上限，并按资料公式计算生命与内力上限。
5. 武学资格逻辑检查等级、属性与门派要求；门派要求为空表示不限门派。测试案例覆盖合格/不合格、升级阈值/跨级/属性上限与重复或悬空引用。
6. 更新 `CHANGELOG.md`、`DEVLOG.md`、`ROADMAP.md`、`README.md`、GDD、架构与数据指南；新增本计划；构建及手动/临时验证通过并提交 `round-04:` commit。

## 可验证子任务

1. **协议与资料**：定义五项核心属性 `body`、`force`、`agility`、`insight`、`resolve`；设计角色模板/门派/武学三份 Schema 与数据，登记到 manifest。Ajv 验证真实数据及若干无效样本。
2. **跨资源与进度引擎**：实现与 Phaser 无关的解析、id/门派引用校验、角色状态初始化、经验阈值/升级成长、生命与内力派生上限和武学习得资格。用临时脚本覆盖正常与边界数据。
3. **游戏加载与文档回归**：把新资源纳入当前 manifest 启动路径；作为可选资料分类，坏数据只警告不阻断地图。浏览器确认 Round 03 世界仍正常显示，再更新项目文档并提交。

## 数据约定

- 角色模板资源 `character-profile.round-04-set`：集合内的模板声明属性起点、等级/总经验起点、最高等级/属性上限、基础与逐级经验、每级属性增量，以及生命/内力的 base、perLevel、属性权重公式。游戏状态仅保存在运行时对象中；存档由 Round 09 负责。
- 门派资源 `faction.round-04-set`：稳定 id、名称、立场/宗旨描述与武学风格说明；不在本轮实现成员资格变更、声望或拜师。
- 武学资源 `martial-art.round-04-set`：稳定 id、名称、类别/风格、简介、适用门派 id（空数组表示不限门派）、最低等级/属性和初始熟练度/上限；招式效果与战斗消耗留给 Round 05。
- 核心属性键和允许范围属于通用协议；显示名称、内容文本、升级曲线、派生公式和门槛均位于 JSON。Schema/结构解析失败时禁用对应可选资源并告警；集合解析成功后，重复 id 保留首声明并告警，武学门派引用逐条校验，只有引用无效的武学被禁用。

## 风险

- 属性与派生公式会成为战斗/存档依赖；本轮将协议保持小而明确，并用数据配置经验曲线与权重，避免下一轮改写运行时公式。
- 只有门派/武学资料而无战斗界面；本轮仍交付可被后续系统调用的进度与资格逻辑，不伪称已有战斗效果。
- 当前 GridScene 将数据错误区分为必需与可选；新资源必须显式加入可选分类并作浏览器回归，避免破坏已有地图。
- 暂不持久化运行时角色状态；页面刷新后的存档恢复安排在 Round 09。
