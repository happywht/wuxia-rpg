# Round 204 计划：既有差事深化 ID 台账与证据闸门

## 目标
把“深化至少12项既有差事”的交付证据落实到稳定任务 ID，并区分资料/自动回归/真实旅程证据，明确哪些差事仍未实走，作为后续补验的可执行清单。

## 用户故事
作为项目负责人，我可以逐项看到哪些原有差事确实承载了调查、战斗/习武、物品/制作或人物立场深化，实际旅程走到了哪一段，以及哪些仍只能算实现或自动验证。

## 验收标准
1. 列出至少12个不同的既有任务 ID，逐一指向其当前资料文件及深化实现来源。
2. 每项标注类别、证据等级、具体可复查的轮次文件，并将未完成真实旅程的项目明确列为待验，不能以自动测试替代。
3. 加入可复跑的校验，确保ID真实存在、无重复、证据路径存在、四类覆盖齐全；脚本不得把 `implemented` 或 `automated` 自动升格为 `played`。
4. 针对该校验添加正反用例；同步 CHANGELOG、DEVLOG、ROADMAP 与权威目标进度并独立提交。

## 子任务
1. 从 Round100–104 原始计划、内容证据和当前任务资料提取稳定ID、任务深化类别与直接证据。
2. 建立 ID 级证据账本及审计脚本/测试，校验资料源和证据文件，保留“尚不能判定12项体验验收已通过”的状态。
3. 运行专项、类型与相关资料校验，写入本轮 verification 并提交本轮明确文件。

## 涉及文件
`iterations/round-204/`、`docs/DEEPENED-QUEST-EVIDENCE.md`、`scripts/audit-round-204-quest-evidence.mjs`、`tests/round204-deepened-quest-evidence.test.ts`、`package.json`、`docs/PROJECT-GOALS.md`、`CHANGELOG.md`、`DEVLOG.md`、`ROADMAP.md`。

## 风险
Round100–104证明的是资料和实现覆盖，不是每项均有真实键盘旅程；后续轮次实走可能只覆盖任务链中的部分阶段。任务文件使用合并资料集，读取时必须按稳定ID定位，不能只靠文件名断定任务被深化。当前工作区存在无关用户更改，提交时只纳入本轮文件。

## 预计人类工程师工时
60–90分钟，包含跨轮证据溯源、ID/类别核对、校验脚本与回归边界复核。
