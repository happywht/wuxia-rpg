# Round 34 计划：世界设定与资料作者手册校准

## 本轮目标

把散落在 GDD、人物志、门派志、任务志和地图资料中的原创江湖设定整理成可引用的世界设定文档，并将地图图册、对白规范和任务规范校准到当前实际资料与 Schema。增加可重复运行的文档一致性审计脚本，避免文档中的区域、人物、任务、条件/效果协议随资料迭代而过期。

## 用户故事

- 作为首次进入项目的玩家或协作者，我希望通过一份世界设定了解雾雨渡口、两地往来、五个门派及药道会盟的由来，而不必从多份任务对白中拼凑背景。
- 作为地图、对白或任务资料作者，我希望地图图册准确说明地图结构与触发资料，规范指南覆盖当前完整协议，并能用命令发现文档和基础 JSON/Schema 的差异。
- 作为长期维护者，我希望文档只陈述当前已实现的玩法和真实资源，不把计划功能写成现有能力。

## 验收标准

1. 新增 `docs/WORLD-SETTING.md`，以现有原创人物、门派、任务、世界地图、气候/历法和对白资料为证据说明背景、地理、势力关系、主要事件和叙事边界；不覆盖或改写任何引擎/剧情数据。
2. 校准 `docs/MAP-ATLAS.md`、`docs/DIALOGUE-GUIDE.md`、`docs/QUESTS.md`：地图 id/区域、关口双向端点、已配置区域事件和地图边界符合当前资料；对白条件/效果种类齐全且语义对应 schema/runtime；20 个任务、目标类型、前置/互斥/失败机制和奖励列表与 JSON 一致。
3. 新增 `scripts/audit-round-34-docs.mjs` 和 `npm run audit:round-34`；从 manifest、地图、NPC、门派、任务、Schema 与对白引擎协议读取事实，发现缺失/多余地图与任务词条、条件/效果种类遗漏、错误地图坐标或当前文档覆盖缺口时以非零退出。
4. 审计不把规划中的功能视作已实现，不硬编码易变的任务/地图总数；以实际数据驱动计数。脚本不访问网络、不修改源文件或文档。
5. 更新 `docs/DATA-GUIDE.md`、`CHANGELOG.md`、`DEVLOG.md`、`ROADMAP.md` 和必要的 GDD/文档索引；运行 Round 34 审计、Schema 校验、类型检查、生产构建及 R33 图谱/R31 任务回归，通过后提交唯一 `round-34:` commit。

## 可验证子任务

1. **世界设定与地图图册**：整理原创世界沿革、渡口地理、门派格局与会盟事件；按当前 map JSON 和 world-map 声明校准区域、起点、关口、落点、事件和地图说明。
2. **对白/任务规范核对**：对照对话 JSON Schema、运行时条件/效果解释器及任务 Schema/引擎，补足流程、字段、错误隔离、20 项实际任务和失败/互斥语义。
3. **自动审计与回归**：实现只读文档审计脚本和 npm 命令；用故意缺失条目或协议种类的临时内存输入验证失败信息，再运行完整资料、引擎回归和构建命令。

## 风险

- 现有设定分散在资料与对白里；归纳时需标明事实来源，不把推测升级成既定剧情。
- 对话 Schema 和运行时交叉语义各有边界；审计脚本应核对静态协议及使用文档，不得擅自改变封闭 Schema 或引擎规则。
- 地图说明涉及程序生成瓦片及阻挡矩阵，需按数据网格生成或校验位置，不能只凭插图/描述猜测可通行性。
- 本轮不改存档协议、玩法条件或任务/对话数据；审计须只读，减少对既有运行时内容的风险。

## 预计人类工程师工时

约 16–24 小时：世界资料交叉阅读与设定整合 3–5 小时；地图图册及两份协议手册校准 5–7 小时；文档审计脚本与错误路径核验 4–6 小时；文档回归、构建和提交 4–6 小时。
