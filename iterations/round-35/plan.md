# Round 35 计划：MOD 优先级、来源追踪与资料作者工作流

## 本轮目标

把现有的同路径 JSON 覆盖机制补成可检查、可解释、易排错的 MOD 工作流：明确多个 MOD 的生效顺序；让运行时能够查到每项资源最终采用的来源；把坏覆盖的具体原因与修复建议呈现给玩家/作者；提供本地命令校验已启用 MOD 并输出覆盖报告。

## 用户故事

- 作为内容作者，我希望一眼确认 `enabledMods` 的优先级和每项资源最后来自哪一层，不必从零散控制台日志推断。
- 作为 MOD 作者，我希望覆盖文件有问题时看到具体文件、校验错误和下一步修复方式，并能在提交前运行命令检查。
- 作为玩家，我希望启用 MOD 后游戏继续使用上一份有效资料；遇到退回时能在游戏内查看原因，而不是只看到一条无法操作的泛化提示。

## 验收标准

1. `enabledMods` 顺序仍是唯一的覆盖优先级来源：从前到后依次覆盖，后声明且校验通过者获胜；坏覆盖不替换上一有效值。
2. 成功装配的 `LoadedWorld` 保留启用顺序、所有已加载资源的最终来源与 MOD 诊断；来源与真实运行时加载结果一致。MOD 来源资源在跨资源装配阶段被部分禁用的警告也须能追溯回来源 MOD。
3. 游戏内新增 F2 资料/MOD 面板，展示启用顺序、各资源最终来源、MOD 错误的来源/文件详情/可执行修复提示；分页及按键锁定正确，关闭后恢复探索输入。
4. 新增 `npm run inspect:mods`：按 manifest 顺序检查已启用覆盖的 JSON 可读性与 schema，报告每个资源的基础/覆盖层及最终来源；缺少某资源覆盖属于正常情况，坏覆盖给出路径与修复提示并以非零退出。注明运行时语义检查仍由游戏加载器执行。
5. 新增 Round 35 专项烟测，覆盖多层先后覆盖、来源报告、坏 JSON/schema 回退与诊断提示；文档说明启用、排序、检查、理解整文件覆盖及在应用内查错的步骤。
6. 更新 `CHANGELOG.md`、`DEVLOG.md`、`ROADMAP.md` 和 `README.md`，运行专项验证、既有 MOD/资料回归和生产构建，通过后提交唯一 `round-35:` commit。

## 可验证子任务

1. **引擎来源与诊断**：为加载器结果/诊断保留 MOD 覆盖来源，补充带有覆盖文件定位及修复建议的结构化信息，同时保证非法覆盖原子回退。
2. **运行时查看与作者命令**：新增 F2 分页资料来源面板，并新增只读 `inspect:mods` 命令输出启用顺序、schema 检查结果和最终有效来源。
3. **失败路径与回归**：用临时 fixture 证明后序有效层优先、坏 JSON/Schema 不夺取来源且报告可行动；更新 MOD 工作流文档并运行回归/构建。

## 风险

- 来源追踪若在装配时丢失会误报 MOD 生效情况；验收以 `LoadedResource.source` 的最终值为真值，并以 fixture 与加载器实测交叉核对。
- 命令行 Schema 校验不能覆盖依赖 NPC/地图/知识图谱的运行时语义校验；命令必须明确范围，不能误称为完整游戏加载验证。
- 小屏面板可能被大量资源与诊断挤满；使用来源分页、错误摘要与可读滚动/翻页方式，避免遮挡或吞掉输入。
- 本轮不支持热重载或字段级合并；MOD 顺序仍由 manifest 显式声明，R36 另做开发期热重载。

## 预计人类工程师工时

约 18–26 小时：来源/诊断协议与回退测试 4–6 小时；运行时来源面板 4–6 小时；本地 MOD 检查工具和多层 fixture 5–7 小时；作者手册、回归、视觉/构建检查与提交 5–7 小时。
