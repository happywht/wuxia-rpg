# Round 37 计划

## 目标

建立可验证、可迁移的 MOD 内容包格式：把当前采用 `mods/<modId>/<data/base 相对路径>` 布局的传统 MOD 导出成带格式版本、引擎兼容范围和完整性校验的单文件包；导入时先做无写入预检，显式应用后只安装到新的 MOD 目录，不改基础资料或自动启用。

## 用户故事

- 作为资料作者，我能将一个已有 MOD 导出为可分享的版本化内容包，并在缺少注册资源、JSON 错误或 Schema 不匹配时得到具体诊断。
- 作为玩家/维护者，我能先预览包的兼容性、资源清单和校验结果；确认应用后，内容只会写入安全的新 MOD 目录，随后由我按现有流程决定是否启用。
- 作为未来的引擎维护者，我能识别不支持的包格式/引擎版本，并将旧式无元数据 MOD 布局明确转换为当前 v1 格式。

## 验收标准

1. 新增包格式 JSON Schema，约束包类型、`formatVersion`、稳定包元数据、引擎兼容声明、唯一资源 ID 与 SHA-256 校验值。
2. 导出器仅读取目标 MOD 对应且已登记在当前基础 manifest 的资源；验证 JSON、资源 Schema 和 MOD id；生成确定性、单文件的 v1 包。
3. 导入器默认只读预检；校验格式/引擎版本、校验和、资源 ID 唯一性、资源是否已登记以及每项当前 Schema；未知或损坏资料给出可定位错误。
4. `--apply` 仅可安装至 `mods/` 下安全的新一级目录；路径由当前可信 manifest 的资源 ID 解析，不接受包内任意写入路径；拒绝覆盖已存在目录；不改 `data/base/manifest.json`。
5. 传统无包元数据 MOD 目录可以经导出命令迁移到 v1 包；未知的未来格式与不兼容引擎版本明确拒绝。
6. 专项烟测覆盖导出/导入往返、只读预检、成功安装、坏 Schema/校验和、重复或未知资源、路径穿越、版本不兼容和目标冲突。
7. 更新数据作者指南、架构/资料协议文档、变更/开发日志与 50+ 轮路线图，并记录命令和验证结果。

## 子任务

1. 定义包清单 Schema、版本/兼容规则、确定性摘要及传统目录迁移语义；实现无副作用导出。
2. 实现预检与显式安装 CLI，限制文件访问到已登记资源和新 MOD 目录，逐类检查故障恢复行为。
3. 建立往返/攻击性输入专项烟测，完善 MOD 作者文档，并通过现有数据校验、MOD 检查、类型检查与生产构建。

## 风险

- 包内资源来自外部，必须先验证 ID 并从当前 manifest 查得目标路径，不能按输入路径拼接落盘。
- 兼容范围比较若接受宽松版本字符串会造成误判；只接受严格三段数字版本，并明确拒绝未知协议版本。
- 安装跨多个文件并非天然原子；通过先完整校验、检查目标不存在、写入同盘暂存目录再改名，避免留下半成品。
- 资源级 Schema 检查不等于运行时跨资源语义装配；文档和 CLI 报告需明确边界。

## 预计人类工程师工时

约 2–3 小时：协议与威胁边界 30–40 分钟，CLI/校验/迁移实现 60–90 分钟，专项故障注入验证 30–40 分钟，文档与路线图校准 20–30 分钟。
