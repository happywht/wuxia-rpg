# Round 50 计划：1.0 最终交付审计与开发复盘

## 本轮目标

按目标文件逐项核验原创武侠 RPG 的最终交付标准；补齐自动化审计与可追溯的验收矩阵；用浏览器实际验证从新游戏到移动、对白、任务、战斗/奖励、学武、存档和读档的玩家路径。只在证据覆盖整项要求时将该项标为通过；外部托管发布、物理手柄等本机不能验证的事项单独列明。

## 用户故事

- 作为项目接手者，我希望能从一份逐项验收矩阵看出目标要求、当前证据、验证方法和缺口，而不需要把历史开发日志当作最终证明。
- 作为内容作者，我希望最终数量、manifest/schema、轮次计划/提交和关键文档由脚本读取实际仓库状态后检查，避免手工统计漂移。
- 作为新玩家，我希望有人实际从浏览器操作完整走通新游戏、战斗成长、物品/武学与存读档，而不仅看到引擎 API 测试。

## 验收标准

1. `docs/FINAL-ACCEPTANCE.md` 对目标文件每项硬性验收逐条列出：要求、当前证据（路径/命令/运行方式）、结果（通过/部分/未验证）及剩余边界；不得把 R50 当成目标自动完成的依据。
2. 新增可重复的最终结构审计命令，从当前 Git 历史和工作树核对 Round 00–50 每轮计划与 round commit、规定数据数量、必需文档、manifest/schema 覆盖及主要 MOD/解耦证据；失败时给出具体路径或缺项。
3. 自动审计不破坏 `npm run check` 的浅克隆 CI；历史依赖审计单独运行，且有成功与反向 fixture 测试。
4. 浏览器手动验收覆盖新游戏、移动、对白、接任务、战斗胜利与奖励物品、学习武学、存档/读档；每一步记录可观察结果和输入路径。未能完成的步骤在矩阵中保留为未通过/未验证，并优先修复实际缺陷。
5. 总结游戏特色、原创创新系统、授权/无远端发布状态与后续路线，更新 README、CHANGELOG、DEVLOG、ROADMAP 及相关发布/测试文档。
6. 运行新审计及完整质量门槛/发布包验证，记录结果；按 `round-50: ...` 提交。

## 子任务（均可独立验证）

1. 读取目标文件并盘点 R00–R50 计划/提交覆盖、当前结构化内容计数、关键文档和 CI/包发布边界；把要求映射为验收矩阵。
2. 实现只读 `audit:final`（或等价专用命令）及正反向测试，验证轮次/提交、计数、Schema、资料目录和文档不变量。
3. 浏览器操作实际玩家纵向路径，覆盖战斗奖励、向导师学武和三个存档槽中的空槽保存/重载；修复任何真实阻断问题。
4. 补全开发复盘、发布快照/后续路线、CHANGELOG/DEVLOG/ROADMAP 并重复验证；在最终状态下运行最终交付审计。

## 风险

- 先前 R46 引擎集成测试不是浏览器完整通关证据；本轮须逐步观察实际 UI 与存档恢复结果。
- 最终审计要区分运行时可证事实与静态扫描推断（尤其“引擎无设定硬编码”）；不让弱扫描代替人工边界检查。
- 新审计读取 Git 历史，但不能成为浅克隆 CI 的必需门槛；需通过独立命令运行并用缺少提交/计划的临时 fixture 验证失败路径。
- 当前无配置的 Git remote，不能验证托管 Pages 实际发布或托管 CI 结果；本轮仅本地构建、打包、解包及浏览器流程。
- 浏览器验收保存数据会修改当前站点本地存储；只用确认为空的槽位，完成后验证读档并如实记录测试存档，不覆盖已有用户存档。

## 预计人类工程师工时

约 90–150 分钟，包含需求证据映射、审计器/测试、浏览器纵向走查、缺陷修复、复盘文档与最终发布包验收。
